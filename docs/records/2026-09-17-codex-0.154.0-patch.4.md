## Fixes

- `codex-rotate`: fixed an idle busy loop where every `codex app-server` built
  with the rotate helper burned ~110% CPU and spawned `codex-rotate rpc` about
  20 times per second. `AuthManager::auth()` unconditionally reloaded external
  auth, each reload minted a new `last_refresh`, and refresh equality (which
  compares the full `AuthDotJson`) published a change for an otherwise
  identical snapshot. App-server's otel reloader reacted to that change,
  waited 50ms, and reloaded config through a path that called `auth()` again,
  closing the loop. Passive `auth()` reads now return the last published
  rotate snapshot without contacting the helper; explicit request admission
  still reacquires from the helper, so account switches remain immediate.
  A byte-identical snapshot also reuses its previous `last_refresh` and HTTP
  client instead of minting fresh ones (and shelling out to
  `lsb_release`/`getconf` for the user agent) on every reload.
- `codex-rotate`: the helper's Unix process group is now killed and reaped on
  timeout or cancellation, not only the direct child.
- `codex-rotate`: startup acquires credentials once instead of twice (a
  temporary helper inside `AuthConfig::load_auth` followed by the installed
  helper resolving again).
- `codex-rotate`: a self-invalidating MCP publication used to fail the calling
  turn after two attempts with no way to settle. It now gets three rounds of
  two publications each, separated by a bounded 50ms pause, before reporting
  that the refresh did not stabilize.
- `codex-rotate`: compaction and same-owner tool work now retain the refreshed
  request credential after a 401 recovery instead of the stale one captured at
  step start.
- `timed-queue`: each `/later` used to spawn a detached due task plus an
  untracked 10-second tick loop, so a removed or replaced entry kept emitting
  stale events for the rest of its original delay. Scheduling now runs through
  one owned, cancellable scheduler keyed by item id and generation, uses
  checked arithmetic for delay/deadline construction, and reconciles wall-clock
  deadlines after system resume (monotonic time alone does not advance across
  sleep).
- `editable-enter-queue`: the same-turn recall RPC used to run inline on the
  single TUI event loop with no timeout, so a slow or lost response froze
  keys, redraws, and app-server events. It now runs in a bounded background
  task, and its completion updates whichever thread (active or backgrounded)
  actually owns the recalled input by `(thread_id, client_id)`, instead of
  only the active thread. Inactive-thread committed-item cleanup now removes
  the exact matching client id instead of assuming the front of the queue.
- `websocket-reconnect`: the liveness probe now has one end-to-end deadline
  covering command enqueue, Ping write, and Pong wait -- previously a pump
  blocked writing an upstream Pong could hang connection reuse indefinitely. A
  pre-suspend pending probe can no longer be satisfied by a post-resume Pong,
  and a successful explicit probe advances the heartbeat schedule so it does
  not immediately re-probe.
- `tui-notification-sound`: spawned player commands are now supervised with a
  bounded timeout, kill, and reap instead of being spawned and forgotten,
  which previously left zombies and could leave a hung player running
  indefinitely.
- `tui-status-line-command`: ordinary and guaranteed frame deadlines are now
  consumed independently. Previously an earlier-firing guaranteed deadline
  could clear the ordinary deadline's slot, causing a duplicate redraw and
  silently dropping the scheduled ordinary refresh.
- `tui-status-line-command`: a renderer that prints and exits without reading
  stdin no longer fails the status line. The runner joined the stdin write,
  the stdout read, and the child wait with `try_join!`, so the broken pipe
  that a child produces by exiting and closing its read end short-circuited
  the join and was reported as "failed to write stdin" -- and the error path
  then killed the child and threw away output it had already written. That
  is the ordinary shape for a status line command, so a broken pipe on the
  write or the shutdown is now read as "this command does not want the
  payload"; the exit status still decides success. Caught by the new CI test
  job, which failed on it on both retries.

## Gate

- All 7 enabled patches applied cumulatively to the pinned upstream SHA with
  both `git apply --check` and `patch -p2` (Nix's actual apply method), each
  verified from a fresh checkout at every layer boundary.
- `nix flake check` passes in CI (`checks.x86_64-linux.codex-patched`,
  `manifest`, `latest-release-ref`, `release-binaries`, `auto-release`); its
  `doCheck` is empty, so it verifies the build but runs no test.
- Added a second CI job (`.github/workflows/check.yml`) that stages the same
  patched tree outside nix and runs `cargo nextest run -E 'kind(lib)'` against
  the pinned 1.95.0 toolchain for `codex-tui`, `codex-api`, `codex-login`,
  `codex-core`, and `codex-app-server-protocol` -- the crates the enabled
  patches add unit tests to. Integration suites (`kind(test)`) are out of
  scope; they spawn whole app-server/core processes.
- That job's own first run caught a real borrow-checker error in this
  release's `tui/src/notifications/sound.rs` test rewrite, and a test-premise
  bug in a `codex-rotate` regression test (`reload_of_a_rotated_rotate_
  snapshot_publishes_an_auth_change` reused a static-response helper for both
  the initial fetch and the reload, so the "rotation" happened before the test
  ever subscribed to auth-change events and the reload just re-fetched an
  already-cached snapshot). Both are fixed; see the port commits.
- Verified locally end-to-end against the pinned 1.95.0 toolchain (installed
  via `rustup` inside the flake devShell, since the devShell's own `nix`-
  provided `rustc` is 1.98.1): `codex-tui` (4371 lib tests), `codex-login`
  (180), `codex-api` (176), and `codex-app-server-protocol` (304, minus two
  skipped) all pass. `codex-core`'s suite hung mid-run under this machine's
  nested `ai-sandbox` bwrap layer and could not be completed locally; CI's
  unsandboxed runner is the environment that can actually finish it.
- `core/config.schema.json`, carried by the `tui-status-line-command` patch,
  placed `StatusLineCommandConfig` before `SkillsConfig` with two fields
  inlined; schemars actually emits it after `SleepToolMode` with every field
  pretty-printed multi-line. A permanent fixture bug, not a version-pin
  artifact -- fixed and reflowed the patch as one diff from the pinned SHA.
- Two more tests overflow their stack on this runner's toolchain/glibc
  combination independent of `RUST_MIN_STACK`: `guardian::tests::
  guardian_ephemeral_retry_preserves_parallel_trunk_and_fork_history` and
  `app::tests::selected_and_resumed_threads_use_server_capability_for_v1_and_v2_children`
  each hardcode their own thread/runtime stack size in source (4 MiB, 8 MiB)
  via `std::thread::Builder::stack_size` / `Builder::thread_stack_size`, which
  takes priority over the env var and so never sees it. Neither is touched by
  an enabled patch; both moved to the CI job's skip list alongside the
  pre-existing five rather than bumping an env var that cannot reach them.

## Known CI job gap

Seven tests are skipped in the new `test` job, all confirmed to fail
identically on a clean, unpatched checkout of this exact tagged commit --
none are touched by any enabled patch:

- `tui/src/app/tests/safety_buffering.rs`:
  `active_turn_interrupt_is_nonblocking_and_coalesces_repeated_requests`,
  `agents_overview_acknowledges_inactive_steer_before_interrupt`.
- `tui/src/pets/mod.rs`:
  `kitty_local_file_pet_image_uses_file_reference_without_inline_payload`.
- `app-server-protocol/src/schema_fixtures_tests.rs`:
  `stable_precomputed_exports_match_schema_fixtures`,
  `experimental_precomputed_exports_match_generated` -- these compare
  `editable-enter-queue`'s carried precomputed schema payloads (`.zst`) against
  freshly generated output. The carried payloads are already stale on
  `origin/main` (predate this release) and have their own regeneration path
  (`.github/workflows/refresh-editable-enter-schema.yml`); not fixed here to
  keep this release scoped to the busy-loop fix and its lifecycle follow-ups.
- `core/src/guardian/tests.rs`: `guardian_ephemeral_retry_preserves_parallel_
  trunk_and_fork_history` spawns its own thread with a hardcoded 4 MiB stack.
- `tui/src/app/tests.rs`: `selected_and_resumed_threads_use_server_capability_
  for_v1_and_v2_children` builds its own tokio runtime with a hardcoded 8 MiB
  thread stack. Both hardcoded budgets overflow on this runner's toolchain/
  glibc combination and neither responds to `RUST_MIN_STACK`, since an
  explicit `stack_size`/`thread_stack_size` call always wins over the env
  default.

Also unfixed, out of scope for this release: `tui-notification-sound`'s
fallback still triggers only on a spawn failure, not on a command that spawns
successfully and then exits non-zero (e.g. `canberra-gtk-play` without a
running sound server on Linux blocks the rest of the platform default chain).
Remote compaction's pre-turn and standalone paths do not yet bind
`step_context.rotate_auth`/residency the way the per-turn path does.
